# LibraryManager — пять подходов к работе с данными

В ходе разработки LibraryManager были исследованы пять подходов к взаимодействию **Application** и **Infrastructure** при использовании EF Core.

Цель экспериментов — сравнить способы организации доступа к данным, управления зависимостями, выполнения запросов и сохранения изменений.

## 1. Сравнение подходов

| Подход | Преимущества | Недостатки |
|---|---|---|
| **1. Direct DbContext** | Минимум дополнительного кода; вся гибкость LINQ и EF Core; простая реализация запросов и проекций | Application напрямую зависит от EF Core и конкретного DbContext; сложнее заменить механизм хранения |
| **2. Minimal Repository + Queries** | Маленький универсальный репозиторий; специализированные запросы вынесены отдельно; Application изолирован от EF Core | Много интерфейсов и классов; увеличение количества зависимостей; потенциальное дублирование запросов |
| **3. Repository + Expressions** | Универсальные методы Find/Any/Count; гибкая фильтрация; компактный интерфейс; возможность реализации разных хранилищ | Не все выражения переносимы между LINQ-провайдерами; сложно реализовать произвольные проекции и группировки; Application формирует условия выборки |
| **4. CQRS (Commands + Queries)** | Разделение чтения и записи; возможность оптимизировать запросы независимо от доменной модели; DTO-проекции и AsNoTracking для чтения | Больше компонентов и интерфейсов; для небольших приложений может быть избыточным; требуется дисциплина в разделении ответственности |
| **5. Repository + Unit of Work** | Application изолирован от EF Core; централизованные операции с сущностями; явное управление сохранением через Commit(); удобная работа с доменной моделью | Репозитории могут разрастаться; специализированные запросы требуют новых методов; чтение полных сущностей вместо DTO может быть неэффективным |

## 2. Реализации в LibraryManager

| Подход | Git-ветка | Особенности |
|---|---|---|
| Direct DbContext | `feature/infrastructure-ef-without-repositories` | UseCases напрямую используют LibraryDbContext |
| Minimal Repository + Queries | `experimental/infrastructure-ef-minimal-repo` | Generic IRepository для базовых операций и отдельные Query Objects; SaveChanges вызывается внутри Add/Remove |
| Repository + Expressions | `experimental/infrastructure-ef-expression` | Generic IRepository с Expression-предикатами и IUnitOfWork |
| CQRS | `experimental/infrastructure-ef-cqrs` | Отдельные CommandRepository и QueryRepository; запись через UoW, чтение с проекциями в DTO |
| Repository + Unit of Work | `main` | Специализированные IBookRepository и IAuthorRepository, общий IUnitOfWork |

## 3. Основные архитектурные выводы

**Repository** абстрагирует операции доступа к данным. При этом специализированные репозитории предоставляют конкретные методы, а Generic Repository — общий набор операций над сущностями.

**Unit of Work** управляет фиксацией изменений. Он позволяет объединить несколько операций в одну единицу сохранения. При использовании общего DbContext вызов SaveChanges обычно обеспечивает атомарное сохранение изменений в рамках транзакции.

**Query Objects** инкапсулируют отдельные запросы и помогают избежать бесконечного расширения интерфейсов репозиториев.

**Expressions** позволяют передавать условия выборки в виде деревьев выражений. EF Core может транслировать поддерживаемые выражения в SQL, а InMemory/FileRepository — выполнять их в памяти через LINQ to Objects.

**CQRS** разделяет ответственность за чтение и изменение данных. Он не требует обязательного использования CommandHandler/QueryHandler, отдельных баз данных или отдельных репозиториев. Эти механизмы — возможные способы реализации.

Все перечисленные подходы не являются взаимоисключающими. Repository, Unit of Work, Query Objects, Expressions и CQRS могут сочетаться в одной архитектуре.

## 4. Практический вывод

В последующих проектах привычным решением стало разделение сценариев на **CommandHandlers и QueryHandlers** с использованием репозиториев.

Для изменения данных удобно использовать доменные сущности, репозитории и контролируемое сохранение изменений.

Для чтения — специализированные запросы, проекции непосредственно в DTO и AsNoTracking там, где это уместно.

Однако архитектуру следует выбирать исходя из требований:

- Простое приложение может обойтись прямым DbContext.
- При необходимости изолировать хранилище полезны Repository и Unit of Work.
- При сложных и многочисленных запросах полезны Query Objects.
- Если требуется гибкая фильтрация через общую абстракцию — Expressions.
- Когда чтение и изменение имеют разные требования, оправдан CQRS.

**Главный вывод:** не существует одного универсального способа организации Infrastructure. Важно понимать, какие именно проблемы решает каждая абстракция, и не усложнять архитектуру без необходимости.
